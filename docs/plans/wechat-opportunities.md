# 微信流式机会卡与原消息回溯

2026-10-03：主人选择修通 WeFlow → SSE，并明确机会卡必须定位到原始群聊消息；新增消息要递补进机会卡并重新综合分析。

## 目标与范围

WeFlow 实际读取指定账号的群消息 → SSE 接收与查询补漏 → 可靠消息存储 → 重新设计增量分析和机会合并 → ShipRadar 私人机会卡 → 精确原消息和上下文回溯。

主人随后纠正范围：机会卡消息合并不参考 Digest 的既有方案，重新设计；当前核心任务仅为解决 WeFlow 密钥/解密。Digest 只作为已有密钥、解密和数据库读取实现的参考。下文增量分析仅为需求记录，待采集修通后再设计实施。

实时的是消息接收；模型按讨论批次分析。群聊卡沿用私人后台边界，不进入公开文章、RSS、API 或 MCP。跳回原消息指私人页面中定位已保存的原文和上下文，不承诺微信客户端消息跳转。

## 增量分析设计（待实现）

1. 每条消息以账号/群/上游消息 ID 定位，保留发言人、发表时间和入库时间；重复 SSE/补漏不能重复落事件。消息 ID 始终保留字符串，不能直接塞入 Digest 的整数 msg_id，需要稳定身份映射。
2. 接收/补漏水位与分析进度分开。分析以入库变更或明确未处理消息集合驱动，覆盖迟到消息、正文修订和撤回；不只用消息发表时间做游标。失败不标记处理成功。
3. 分析任务固定输入范围，每个群串行或显式版本校验；期间到来的消息留给下一批。重复任务应幂等，证据、卡片修订和处理进度原子提交。
4. 消息随到随存；讨论安静后触发，连续活跃讨论设最长等待时间。具体时间和批量上限在真实消息量和费用实测后确定。
5. 输入包含新消息、讨论上下文和候选旧卡的原始证据。模型区分新机会、同一机会补充、纠正/反证、无关讨论；共用产品名不足以证明同一机会。
6. 更新同一机会保持卡 ID 和收藏/反馈，关联新增证据，重新生成当前结论、可信度、待验证问题和行动建议。旧核查标过期；反证可降低或否定原机会，撤回证据不再参与判断，页面不保留已撤回正文。
7. 重新分析受影响卡时审视全部有效相关证据；超出模型上下文时分段归纳并保留消息引用，再进行综合，不能仅从旧摘要继续滚动而丢失原证据。跨天/跨群只合并确认同一机会的材料，证据始终保留群和发言人归属。
8. 跨卡综合层对更新后的完整候选集重排并折叠重复项，不把群发消息次数当独立证据。定期复查跨批次关联、矛盾和过期机会，首版以正确证据和保守合并优先。
9. 每次卡片修订记录触发消息和修订版本，能解释增加/更改的判断；所有源消息 ID 必须在实际输入证据中存在，禁止模型虚构引用。

## 验收用例

- 新机会生成一张卡，卡上证据入口定位到准确群、发言人、时间和消息上下文。
- 同一讨论第二批补充保留卡 ID，证据递补；重复上报不新增卡或重复调用。
- 后来反证能修正/降低原结论，撤回后原文消失、引用状态和结论同步更新。
- 迟到/跨天补漏不遗漏，失败重试不丢分析范围；卡片更新过程中到来的消息进入下一批。
- 同名产品不同场景不会误并；确认同一机会的跨群证据可联合评估但不丢归属。
- 每次分析绑定输入/证据版本；重新排序可反映更强证据或过期信息，旧核查明确过期。
- 测试采用模拟群聊与本地 stub；真实验收另行记录，不把模拟通过写成真实接通。

## 多库与单密钥接口源码核对

- 当前本机 WeFlow 4.3.0 已有多库能力，不能由一个密钥输入框断言其只支持单库。wcdbCore.ts 的 listMessageDbs / listMediaDbs 调用 native 枚举消息库和媒体库；消息游标以账号 handle 查询。
- 调用链为 chatService.connect 读取单个 decryptKey → wcdbService.open worker 代理 → wcdbCore.open 定位 session.db → wcdb_open_account(sessionDbPath, hexKey, handleOut)。后续查询复用账号 handle。TypeScript 层没有发现逐库 key-map 或明确的逐库加密密钥派生实现。
- Mac 提取器同样委托 xkey_helper 二进制；读取组件 libwcdb_api.dylib 的内部实现未在本地仓库公开。仅凭 hexKey 命名、64 字符格式或 with_key 导出符号，无法确定输入是原始逐库 key、派生前密码，或 native 如何处理其他数据库。没有源码证据不能宣称已确认其内部算法。
- keyServiceMac.ts:490 识别 helper 日志 `[MASTER] hex64=`，并从 JSON key/result 回填单个输入。这是提取器面向 master key 的意图线索，不能仅凭日志标签证明具体派生算法或实际成功获取。
- SQLCipher 官方说明：同一 passphrase 可结合各库不同 salt 派生不同加密 key；原始 32 字节 key 输入则直接使用，不走该密码派生。因此“各库加密 key 不同”不等于“界面必须输入多把密码”。这只是 SQLCipher 机制，不是已验证的 WeFlow/微信实现。
- 当前实测 session 原始 key 无法通过 contact / message 首页校验，只证明该原始 key 不能直接通用；不证明统一上游密码不存在。Digest 的逐库原始 key-map 已验证核心七库主体可读，不能直接当成 WeFlow 的原输入类型。
- 下一步决策应以原生组件期望的 key 类型及实际应用内多库读取结果为依据；不能只因一个输入框就决定替换后端。本轮仅核对源码和更新结论，未修改 WeFlow 代码、密钥或配置。

依据：本地 WeFlow electron/services/chatService.ts、wcdbService.ts、wcdbCore.ts、keyServiceMac.ts；Digest find_key_memscan.py / decrypt_db.py；https://www.zetetic.net/sqlcipher/design/ 与 https://www.zetetic.net/sqlcipher/sqlcipher-api/#key。

## 主密钥类型核实与修复接入点（继续排查）

### 已确认的新证据

- WeFlow 作者在 issue #917 回复与本案完全相同的“其他项目得到多把密钥，WeFlow 能否使用”问题，明确答复其他项目拿到的是派生密钥，WeFlow 需要主密钥，不能直接使用。出处：https://github.com/hicccc77/WeFlow/issues/917 。因此上一节“不能确认输入类型”的状态已由维护者明确说明更新，不能再建议直接回填 Digest 的 session key。
- 本机 libwcdb_api.dylib 的 arm64 静态检查显示：wcdb_open_account 将 hex 输入经 HexToBytes 转成字节，存于账号上下文，再用 WCDB::Database::setCipherKey 设给数据库；GetOrCreateMessageDb 通过 GetOrOpenExtraDb，后者从同一账号上下文取字节设给其他库。没有执行打开账号、没有修改二进制或安全保护。静态检查文件仅位于 /private/tmp。
- WCDB 官方源码 AbstractHandle::setCipherKey 调用 sqlite3_key(handle, data.buffer(), data.size())；CipherConfig 会在首次派生后缓存当前库的 raw key。官方源码核对固定到 Tencent/wcdb 39dd797099d41cf1953d5668acd8cb608016c599，文件 src/common/core/config/CipherConfig.cpp、src/common/core/sqlite/AbstractHandle.cpp、src/cpp/core/Database.cpp。它支持理解调用语义，不能据此宣称本机 native 的全部实现与最新源码逐字一致。
- 对当前账号七个核心库增加加密首页验证：已有各自 raw key 全部通过；把各自 raw key 当 passphrase，按 SHA512 / 256000 次 / 文件 salt 再派生，七库全部不通过。只读加密第一页，无密钥/正文输出。这是具体派生参数下的否定结果，不是所有可能算法的穷举，也没有提取到主密钥。
- 另一个公开实现 weflow-cli 的 initKeyService.ts 明确说明 passphrase → 各库 raw key 的派生，并有跨消息分片读取；固定参考提交 81ba42c976888b1521307a494b6d88f25411ef96。其主密钥自动提取适配说明涉及 Windows 微信 4.1.12.55，不能当作 macOS 4.1.15 的现成修复。下载源码只作阅读，没有运行其提取/配置逻辑。

### 两条路线的具体实现差异

1. 保持原版原生读取：获取真正的主密钥，修复 Mac helper 对当前微信版本的函数定位/提取；之后在实际应用环境验收 session/contact/多消息库及 SSE。现有逐库派生 key 不能通过逆向 PBKDF2 直接还原主密钥；原生 helper 没有随仓库提供源实现。未找到已验证适用当前版本的现成补丁，本轮不再重复运行失败的 hook、不降级微信、不改 SIP。
2. 增加逐库密钥读取模式：在 WeFlow worker 数据层选择显式 key-map reader，保持 httpService.ts 的查询/SSE 契约与 messagePushService.ts 的事件处理。涉及 chatService.connect 的单 decryptKey 校验、wcdbService 的 worker 入参、wcdbWorker 的读取后端选择与一个新的只读 reader；若增加配置字段则只改项目代码定义，真实密钥路径/认证配置待具体授权。reader 必须读取有效 WAL 或一致性快照，不能把 immutable 的库主体验证当实时成功。需覆盖已轮转的 message_1..5、稳定字符串消息 ID、显示名、增量监控和撤回事件；不扩展到朋友圈/媒体/其他账号，不改数据库 schema。

SSE 依赖并非只有一个查询入口：messagePushService 调用 getSessions、getNewMessages、getMessageTableStats、execQuery、群昵称/显示信息，消息监听来自 wcdbService.setMonitor。逐库模式必须补齐这些实际依赖并验收查询补漏，不能只替换 open() 就宣称 SSE 修通。

已向主人提交上述读取架构选择（逐库模式为建议路线）。这是实现方向确认，尚未得到选择；本轮可独立完成的源码与密钥类型核对已完成，未改 WeFlow 代码、真实配置或密钥文件。WeFlow → SSE 仍未修通。

## 主微信使用与消息准确性约束（主人补充）

主人明确：不要求秒级，1、2、10 分钟延迟均可接受；不能错乱消息，尤其不能把 A 群消息归到 B 群。接入账号为主微信，保护正常登录、使用与账号状态优先于采集时效。本次补充不是授权进程附加、Hook、自动重登、修改安全设置或密钥配置。

- 建议首版以 10 分钟批量采集为默认设计假设，SSE 用于把每批有效变化推给 ShipRadar，不再依赖微信进程 Hook 或秒级文件监听。
- 仅复用已验证的逐库密钥。新库、密钥轮换或身份校验失败时报告缺口、停止该库导入，不自动重新扫内存、提取主密钥或切换账号。
