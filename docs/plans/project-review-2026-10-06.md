## 具体问题（按优先级）

### P1：研究任务崩溃后可永久停在 queued

- `packages/backend/src/research.ts:37` 写 queued，只有处理函数正常完成或进入 catch 才更新状态。
- `packages/backend/src/jobs/queue.ts:55` 配置零重试、300 秒过期；`operations/recover.ts` 没有研究状态对账或失联任务恢复。
- `apps/web/app/routes/admin/research.tsx:30` queued 时持续轮询并禁止继续提问。进程被强制终止、未能执行 catch 时，队列失败不会同步更新会话。
- 建议：对账队列与业务状态，提供使用同一回执身份的恢复入口；必须区分已取得结果、结果未知、可重试，避免重复付费。
- 归档也有类似状态漂移：`sources/mp-archive.ts:32` 即便 workingUntil 已过，running/queued 仍会阻止重新开始；用户需要手动暂停再继续，而非自动识别失联。
- 验收：worker 在请求前/回执持久化后强制退出，重启后状态能结束或明确恢复，不永久转圈、不重复买结果。

### P2：“获取缺失全文”漏掉普通采集文章，并永久跳过空正文

- `packages/backend/src/sources/mp-archive.ts:94` 仅选择 `raw.mpArchive=true`，并排除 `mpBodyFailed`。
- 同文件第 79 行跳过已有文章，不会为普通采集的缺正文文章补归档标记；第 101 行遇空正文写失败标记，未找到显式重试入口。
- `apps/web/app/features/admin/MpArchive.tsx` 按钮称“获取缺失全文”；`routes/mp-article.tsx` 无全文提示引导管理员补齐归档，但部分文章无法通过此入口修复。
- 建议：明确按钮处理范围；支持普通采集缺正文与显式失败重试，并保持不自动分析、不自动重复计费的约束。
- 验收：普通采集缺正文、历史缺正文、曾返回空正文三类文章，均有准确状态与可解释操作。

### P2：研究命中正文后丢弃实际命中段落

- `packages/backend/src/publication/research.ts:24` 可匹配整个 body_text；第 25 行按发表时间而非相关度取最多 5 篇，第 29 行始终截取开头 9000 字符。
- 如果答案位于长文后半段，检索虽命中文章，模型实际拿不到命中证据；新文章中的弱匹配还会挤掉旧文章中的强匹配。
- 建议：先做关键词相关性排序、围绕命中位置抽片段、带段落出处，无需立即引入向量数据库。
- 验收：关键证据位于 9000 字符后，仍能进入引用；强相关旧文优先于弱相关新文。

### P2：网络失败后改问题，会复用旧问题的幂等标识

- `apps/web/app/features/admin/action.ts:37` 按 method/path 保存 key，失败保留 key，与请求体无关。
- `packages/backend/src/research.ts:32` 命中 key 后直接返回旧轮次，不比较 question/articleId/scope/previousId。
- 触发：问题 A 已落库但响应丢失，用户改成 B 再发，仍返回 A。新问题被静默丢弃。
- 建议：key 绑定不可变提交快照；同 key 不同请求体返回冲突，相同请求体重试继续复用。
- 验收：响应丢失后原问题重试不多付费；修改问题后不返回旧问题冒充成功。

## 设计判断（改进建议，不等同于 bug）

1. **产品重心分散。** 导航并列精选、发现、全部、热点、日报、主题、公众号。对个人晨读，发现和收藏更接近主线；研究还缺将结论存为可跟踪调查项的闭环。建议先确定“发现 → 阅读 → 研究 → 保存结论/下一步”的主流程，暂缓继续扩大入口。
2. **热度不等于机会。** 既有多源讨论、48 小时窗口、日报机制适合新闻热点；低关注、长时效的细分需求不一定在这种排名中突出。保留资讯视图，同时用真实晨读样本评价机会发现质量，不凭感觉改分数。
3. **公开全文权限与私人研究材料绑在一起。** `publication/research.ts:19` 受 site_fulltext 限制，已抓取但不可公开全文的资料只能用摘要研究。这符合目前公开读取边界，但限制私人研究效果。如需私有全文研究，应先明确内容使用权限与独立访问边界，不能靠打开公开全文解决。
4. **settings 承载了业务数据。** 每轮问答、引用片段、幂等映射与归档任务都放 settings；当前规模可用，但缺少会话索引、业务状态约束和专门保留策略，后续历史检索、清理、对账会更难。先补生命周期，再在有实际规模需求并获 schema 变更授权后决定独立表。
5. **验证与文档缺统一现状。** 多份计划混合不同时期结果，且完整数据库测试依赖空库、共享预算与队列。应有单一当前状态清单，以及可重复的独立测试库基线；不能直接将旧失败归为环境问题后忽略。
